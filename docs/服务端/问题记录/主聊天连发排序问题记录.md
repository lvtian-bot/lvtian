# 主聊天连发排序问题记录

## 当前结论

回复记录在任务启动时创建；此前实时更新留在原位，重连又按创建时间恢复，所以同轮补充可能落到答复后面。现改为保留完整后台回复，并在引擎实际接收补充时保存正文边界；聊天页只投影显示位置。完成时间仍来自服务端 `completedAt`，不参与全局排序。不修改通知、同步游标、用户文案或运行服务。

兼容边界：旧记录没有补充接收时的正文偏移，无法可靠辨别当时已显示的过程文字，因此维持原顺序，不伪造历史。新记录的接收边界随日志、快照和缓存保留。真实设备上的滚动与流式视觉验收尚未执行。

## 2026-11-24 复现与修复

- 基线：main `598ce2369253ac891f82cd3033ba32fb2e38d2d1`（0.3.7）。隔离构造首条输入、启动占位、两条同轮补充，按原对账/显示算法得到 `u1,a1,u2,u3`，预期 `u1,u2,u3,a1`，断言失败。
- 真实边界是服务端提供给引擎的 `takeSupplement` 回调，不是消息入队，也不是工具调用结束。每次成功取走输入后记录当前回复的 UTF-16 正文长度、补充 ID 和受理时刻；边界由现有流式事件传递，客户端完整对账恢复同一数据。
- 聊天展示投影按边界切正文，已有过程文字留在先前位置，后续全部文字接到对应补充后。连续无新正文的多条补充合并到最后位置；工具分段只决定同一位置内的正文气泡，不用于推断最终答复。
- 先投影再倒序、分页，日期使用展示位置所属日；最后可见正文气泡仍使用完成时间，即使补充后没有可见正文也不丢失时钟。首段 key 保持不变；普通消息不重建。复制、工作记录、持久化继续读取完整原文。

## 2026-11-24 空尾段完成时钟回归

独立复核发现：补充在已有正文全部输出后被消费，随后没有可见正文时，初版只把 `completedAt` 放入空尾段，导致已有正文气泡显示开始时间。先新增真实 ChatScreen 气泡回归，空串、纯空白、仅工具三项均复现失败（预期 12:11，实际 12:05）。修复只在展示投影中把完成时间保留到最后可见正文，不移动它、不新增正文、不改变持久化。正常补充后有答复时仍由后续答复显示完成时间。
