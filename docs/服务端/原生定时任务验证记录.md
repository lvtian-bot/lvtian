# 原生定时任务验证记录

## 当前结论（2026-10-26）

原生宿主可以不迁移 ACP 主聊天独立启动。已真实跑通回环鉴权、官方 Node Remote、原生模型工具创建任务、宿主重启后无客户端在线时的到期执行，并以不激活模型的冷读确认真实完成；主聊天实际工具创建链路及 daily/weekly 管理操作亦已通过真实探针。按用户收窄后的首版，App 仅 GET 展示服务器任务/触发记录/结果，页面已实现且通过本地测试；不做 App 管理表单、完成停止、主聊天通知或系统推送。尚未生产启用；云端检查和 Codex 审查必须绑定 PR 最新提交另行核验，不能从本地测试推断。现行代码边界见 [自动任务架构与接口](../自动任务/自动任务架构与接口.md)。

- 任务工作树：`lvtian-native-schedule`，分支 `feat/native-schedule`。
- 脚本：`server/scripts/native-schedule-probe.mjs`。默认只测试认证与空目录；`--execute` 会调用 **DeepSeek 官方 API / deepseek-flash** 创建和执行一个纯文本验证任务，需要调用者通过受控环境继承凭据，脚本不读取生产凭据文件。
- 不涉及生产守护、端口、现有 ACP profile 或 App 发布，不安装第三方依赖，不更改上游包。

## 实际装配与边界

1. 使用已安装的 `@deepseek-ai/dsh@0.2.1-rc.3` 官方 `web` 组合，而不是自写调度器或瘦宿主插件。回环绑定 `127.0.0.1`，端口 `0` 由操作系统分配；不打开浏览器。
2. 每次验证创建权限受限的独立临时根；`DSH_HOME` 隔离 profile、会话、存储与认证，`DSH_AGENTS_HOME` 另行隔离全局指令/技能。仅换 profile 不足以隔离数据。后续加固将 HOME/XDG 指向临时根，子进程环境采用白名单。
3. 启动 URL 含令牌，只经监督进程私有管道捕获，不写入日志。`GET /connect` 的令牌交换得到 API Cookie，同一 Cookie 用于 HTTP 与 WebSocket；socket 断开后重新交换。不能拿 Bearer Token 直接访问原生接口。
4. Node 使用官方 `dsh-typert-registry/client`、`dsh-client-connection/client`、`dsh-api-gateway/client`，再 `$mount()` 官方 Session 与 Schedule `/remote` contribution；不使用当前版本实际为浏览器 loader 的 `dsh-api-remotes/client`，不添加 window shim。
5. 原生创建没有公开 Remote create；通过普通独立根会话的 `standard` preset 实际调用 `schedule_create`，然后读取 catalog 确认。发送消息是 `session.prompt`，不是不存在的 send 方法。
6. `lastDelivery` 仅证明持久收件箱投递；必须关联原生 messageId、真实 assistant 文本和同 turn 的 completed 终态。不能看到 inactive 就认为执行成功。
7. `session.follow` 发送首次快照后会激活会话；离线执行证据只能使用首次快照中已存在的事实，或用不激活 Agent 的 `projections` + `page` 冷读。不能等待观察后新事件再声称无人连接时已经执行。
8. 原生默认组合还包含会话日志上传与遥测。首轮使用的是无私人资料的合成测试会话；加固版通过隔离 overlay 关闭这两个插件，后续接入不得把默认行为当作已经获得生产资料上传授权。

## 实测过程

### 回环认证与目录

- 首次尝试用启动 URL 在根路径换 Cookie 失败；改用官方 `/connect?...&interactions=none` API 接入。
- 修正后脚本退出 0：匿名 `/api` 返回 401，认证后的官方 `schedule.catalog()` 返回空数组。

### 首轮真实创建、重启、无人在线执行

- 普通独立根会话：`session-15251994-9a07-4769-9f00-67b1f94997ec`。
- 原生任务：`schedule-58883290-bd41-44a4-8df8-814579e51245`。
- 原生规则：after 90 秒；UTC 到期 `2026-10-26T06:40:45.819Z`。
- 创建后释放全部 Remote 客户端，终止隔离宿主，再使用同一隔离数据根重启；随后 115 秒内没有 App、浏览器或 Remote 客户端。
- 随后首次历史快照已有 assistant/message seq 35，精确正文 `LVT_SCHEDULE_PROBE_OK`；同 turn 2 的 turn/end seq 37 为 `completed`。
- 初版脚本只打印事实而没有严格断言，因此此轮作为事实证据，不把单纯 exit 0 当完整自动验收。

### 断言与隔离加固

只读交叉审查发现并修正：任务唯一性/规则检查缺失、仅有 snapshot 即成功、全量历史输出过大、客户端释放异常可能跳过宿主清理、环境继承过宽。

加固后第一次运行因严格要求 kind=after 被拒绝。读取隔离 schedule.json 确认模型用等价 `at` 规则创建了正确名称和提示词；因此验收应允许原生 after/at 两种一次性表达，并验证实际时点容差，不能为了通过测试改变产品语义或让模型必须选择某个字段。

加固版真实运行退出 0：会话 `session-ca965090-cdb5-43f3-82d1-3a67e639367f`、任务 `schedule-c4840489-7104-4d87-9225-f5f7f3a9d389`；原生目标 `2026-10-26T06:45:51.582Z`，持久投递 `06:45:51.793Z`。重启且无客户端在线后，cold `projections` + `page` 找到关联收件消息、精确 assistant 输出（seq 32）及 turn 2 的 `completed`。没有调用 follow 或 prompt 来唤醒该次工作。

已把断言抽为 `nativeScheduleProbeAssertions.mjs`，并加入 5 项本地测试覆盖等价 after/at、重复/错时规则、投递与执行区分、旧指令含同样文字、其他 turn、截断、失败与观测后才结束等误判。随后又补入最终回答/禁用工具调用反例。

## 可复用接入代码（尚未挂到正式服务）

- `server/src/nativeTaskClient.ts`：官方 Node Remote 的回环连接适配、受控令牌交换、内存 Cookie、超时/认证/断线失效与错误脱敏；写请求不自动重放，结果未知时交由业务层对账。16 项注入测试已通过。
- `server/src/nativeTaskHost.ts`：启动/停止独立原生宿主、独立数据根、关闭默认日志上传与遥测、不透出启动令牌；重复 start 合并为一次。
- `server/src/nativeTaskHostRunner.ts`：调用官方 `runCli()`（仅 import 不会执行，因为上游使用 import.meta.main 门禁）；在 Harness 进程自身持有 Node 内置 SQLite 的排他事务作为目录使用租约。租约不保存任务数据、不触发执行，用于避免 JSON 存储被两个进程共同写入，进程崩溃或主机重启后由操作系统释放。监督进程管道 EOF 时终止宿主，防止父服务退出后留下不可管理的调度孤儿。
- 宿主/客户端真实组合 smoke 已退出 0，成功认证并读取空原生 catalog；没有模型调用、没有生产服务连接。首次组合 smoke 因只 import 上游入口而超时，定位 import.meta.main 后改为显式 runCli 并验证通过。
- 探针随后已改为直接复用这些类，不再维护另一份连接/进程实现。再次真实全链路运行退出 0：任务 `schedule-b90bba33-e703-44f8-8c71-89207beb93c1`，目标 `2026-10-26T06:59:27.592Z`，持久投递 `06:59:27.732Z`，seq 32 精确结果及 turn 2 completed。断言还要求完成时间早于重连观测，不允许把观测触发的执行当成离线成功。
- 不把这些尚未挂接的类描述成对手机已可用的 API；任务范围授权、创建关联及结果交付仍待业务层实现。
- 当前全量服务端测试 **131/131 通过**，包含宿主租约独占、强杀后恢复、监督管道关闭清理、分块令牌解析、连接鉴权与错误脱敏；`git diff --check` 通过。
