# 三路合并与乐观锁机制

> 本文档深入解析绿天的冲突解决核心算法、ETag 乐观锁机制、影子文件系统 (.shadows/) 以及用户交互选项。

---

## 1. 三路合并算法 (Three-Way Merge)

### 1.1 三版本数学模型
三路合并依赖三个版本的内容：
- **L (Local)**：本地当前文件内容
- **C (Cloud)**：云端最新下载的内容
- **S (Synced / Base)**：上次成功同步时的基准版本（保存在影子系统）

### 1.2 判定逻辑与智能合并 (Smart Merge)
当 `L !== S` 且 `C !== S` 时，说明发生了双向修改（并发写入）。系统不会立即报错打断用户，而是启动智能合并引擎：

1. **行级差分**：利用 `diff-match-patch` 算法分别计算 `diff(S -> L)` 与 `diff(S -> C)`。
2. **冲突区域判定**：
   - 若本地与云端的改动发生在不同段落/行，补丁自动无损应用。
   - 若为闪念笔记，按条目的时间戳（`## YYYY-MM-DD HH:mm:ss`）进行时间线拓扑排序合并。
   - 若为待办事项，按任务行进行状态合并。
3. **不可自动合并的冲突**：同一行存在不可裁决的互斥修改时，放弃自动合并，降级为用户手动决策模式。

## 2. 乐观并发控制 (Optimistic Locking)

### 2.1 ETag 与条件请求
为防止多个客户端并发覆盖，绿天全面引入基于 HTTP ETag 的乐观锁机制：
- 上传文件时，必须携带云端已知的旧 ETag 作为条件：
  - 腾讯云 COS：请求头带 `If-Match: "etag_value"`
  - WebDAV：请求头带 `If-Match: "etag_value"`
- 若云端在此期间被其他设备更新，云端将返回 `412 Precondition Failed`。
- 本地捕获 412 后，将该文件的 `uploadState` 标记为 `'conflict-failed'`，触发 Stage 2 自动救援流程。

## 3. 影子文件系统 (Shadow File System)

### 3.1 设计目的
纯文本的冲突比对必须拥有可靠的公共基准祖先（Base）。如果仅有本地与云端两份文件，无法区分某行是“本地新增”还是“云端删除”。影子文件系统即用于在本地持久化“上一次成功同步的一致性副本”。

### 3.2 物理存储路径
```text
${FileSystem.documentDirectory}/
├── notes/
│   ├── work.md
│   └── flash_notes.md
└── .shadows/
    ├── notes/
    │   ├── work.md.base          # work.md 的同步基准镜像
    │   └── flash_notes.md.base   # 闪念笔记的同步基准镜像
```

### 3.3 影子快照更新时机
1. **上传成功时刻**：本地写入云端并收到 200/204 成功响应后，立即将当前本地内容同步写入 `.shadows/`。
2. **下载覆盖时刻**：从云端全量拉取新内容写入本地工作区时，同步写入 `.shadows/`。
3. **清理时机**：当用户在云端和本地彻底删除文件时，对应的影子副本同步销毁。

## 4. 人工冲突处理三大选项

当智能三路合并无法自动解决冲突时，前端 StatusBanner 提供三种决策路径：

1. **使用云端 (Use Cloud)**：
   - 丢弃本地所有未同步改动。
   - 用云端最新内容覆盖本地工作区文件与影子副本。
   - 清除冲突标记，恢复 `synced`。
2. **使用本地 (Use Local)**：
   - 强行覆盖云端。
   - 忽略 `If-Match` 乐观锁约束或刷新云端 ETag 后强行上传当前本地内容。
   - 上传成功后更新影子文件，恢复 `synced`。
3. **存为副本 (Save as Copy)**：
   - 将本地修改内容另存为新文件（例如 `文件名 (本地冲突副本 YYYY-MM-DD).md`）。
   - 将原文件名重置为云端最新版本。
   - 两个文件各自独立进入同步生命周期，零数据丢失。
