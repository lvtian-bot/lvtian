## 历史排查档案与技术约束

### 1. 文件显示“冲突”状态无法解除（影子文件异常）
- **现象**：用户在界面上无论点击“使用云端”还是“使用本地”，刷新后依然提示冲突。
- **根因分析**：
  1. `.shadows/` 目录下的基准文件由于异常断电或存储权限被系统清空，导致三路合并丢失基准版本。
  2. 文件编码异常：存在非 UTF-8 编码的特殊字符，导致两端计算哈希反复抖动。
- **尝试方案与结果**：
  - *方案 A（失败）*：仅清除 Store 中的冲突标记。结果：下次三阶段检查时重新检测到哈希不符，再度触发冲突。
  - *方案 B（成功）*：在解决冲突的回调中，显式重置 `syncedHash`，并强制将选定版本回写到 `.shadows/`。
- **必须保持的技术约束**：
  - 任何人工冲突解决操作，必须包含「更新物理文件 + 更新影子镜像 + 刷新 Store ETag」三步事务。

### 2. 同步状态长时间卡在“正在检查 (checking)”
- **现象**：顶部状态栏一直转圈，UI 不响应新的同步触发。
- **根因分析**：
  - `SyncService` 中的网络请求未设置全局超时控制，当网络弱网或断流时，Promise 挂起未 settle。
- **尝试方案与结果**：
  - *方案（成功）*：为底层 `fetch` / 云端 API 增加 `AbortController` 并在 15 秒强制超时兜底，捕获异常后将 `syncStatus` 释放并置为 `'error'` 或回退。
- **必须保持的技术约束**：
  - 所有网络 IO 必须包含超时熔断与 `finally` 块状态重置保障。
