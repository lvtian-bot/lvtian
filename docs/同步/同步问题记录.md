## 历史排查档案与技术约束

### 1. 文件显示“冲突”状态无法解除（影子文件异常）
- **现象**：用户在界面上无论点击“使用云端”还是“使用本地”，刷新后依然提示冲突。
- **根因分析**：
  1. `.shadows/` 目录下的基准文件由于异常断电或存储权限被系统清空，导致三路合并丢失基准版本。
  2. 文件编码异常：存在非 UTF-8 编码的特殊字符，导致两端计算哈希反复抖动。
- **尝试方案与结果**：
  - *方案 A（失败）*：仅清除 Store 中的冲突标记。结果：下次三阶段检查时重新检测到哈希不符，再度触发冲突。
  - *方案 B（成功）*：在解决冲突的回调中，显式重置 `syncedHash`，并强制将选定版本回写到 `.shadows/`。
- **必须保持的技术约束**：
  - 任何人工冲突解决操作，必须包含「更新物理文件 + 更新影子镜像 + 刷新 Store ETag」三步事务。

### 2. 同步状态长时间卡在“正在检查 (checking)”
- **现象**：顶部状态栏一直转圈，UI 不响应新的同步触发。
- **根因分析**：
  - `SyncService` 中的网络请求未设置全局超时控制，当网络弱网或断流时，Promise 挂起未 settle。
- **尝试方案与结果**：
  - *方案（成功）*：为底层 `fetch` / 云端 API 增加 `AbortController` 并在 15 秒强制超时兜底，捕获异常后将 `syncStatus` 释放并置为 `'error'` 或回退。
- **必须保持的技术约束**：
  - 所有网络 IO 必须包含超时熔断与 `finally` 块状态重置保障。

### 3. 本地物理文件缺失但哈希一致时盲目跳过下载导致闪念笔记空白
- **现象**：应用更新升级（如沙盒目录调整）或本地缓存丢失后，进入闪念时间线显示空白（`-- End of Timeline --`），而右上角状态却打着绿色对勾显示“已同步”。
- **根因分析**：
  1. `SyncService`（包括 `checkSyncStatus` 与 `syncBatchFiles`）在判断文件同步状态时，仅单纯比对了云端 ETag 与本地 Store 元数据记录的 `localHash`。若两者一致，则直接判定为 `synced` 并 `continue` 跳过。
  2. 同步判定逻辑中缺失了对“本地磁盘上物理文件是否存在”的校验。当本地文件物理缺失而元数据仍记录已同步时，造成“假同步”，云端文件无法自动重新下载拉回。
  3. `useFlashNoteList` 在初次未加载到文件时，后台同步完成触发更新事件时因已加载列表为空而提前返回，未联动重新加载。
- **解决方案与结果**：
  - *方案（成功）*：
    1. 在 `checkSyncStatus` 与 `syncBatchFiles` 比对哈希前，强制校验本地物理文件存在性。若云端存在而本地物理文件缺失，坚决归类为需要拉取（`cloudNewer`），无条件从云端重新下载落盘并纠正元数据。
    2. 在 `FileSystemService` 启动初始化中加入历史沙盒目录（`mdnote_docs` -> `lvtian_docs`）的自动平滑迁移机制，确保既有离线笔记和数据完整继承。
    3. 在 `useFlashNoteList` 的数据刷新监听中，当已加载列表为空时主动调用 `fetchLocalData()` 重新扫描并加载。
- **必须保持的技术约束**：
  - 同步引擎进行任何“已同步（跳过）”或“本地更新（上传）”判定前，必须以本地物理文件的真实存在为前提。若本地物理文件缺失而云端存在，唯一正确的行为是从云端拉取下载。
