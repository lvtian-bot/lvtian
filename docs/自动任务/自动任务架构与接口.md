# 自动任务架构与接口

## 状态与边界

任务规则与执行保存在服务端，App 仍仅只读展示服务器任务与结果，不提供新建/编辑/删除/完成停止。任务页缓存修复 PR #40 已合并（main `8b3b9f1`）并发布 production OTA，真机验收另行跟进。新增服务端任务结果汇报：完整结果先交固定 `main` 主聊天代理，代理向主聊天报告，不强制摘要（Git 同步保留全部仓库明细）；不旁路代理直接贴任务输出，不新增系统推送。结果汇报尚未部署，生产验收待完成。交互范围见 [只读展示说明](界面交互稿.md)。

自动任务与人工待办、Agent 单轮 todo_write 不同。时间规则、下一次运行、持久投递和任务会话均归 DeepSeek Harness 原生 Schedule 所有；绿天不计算权威运行时点、不建立可驱动执行的第二份规则表。

## 服务器存储位置

| 内容 | 位置与归属 |
|---|---|
| 权威任务规则和投递历史 | `<dataDir>/native-tasks/home/storages/schedule.json`，Harness 原生维护 |
| 独立任务会话、执行过程和结果 | `<dataDir>/native-tasks/home/sessions/`，Harness 原生维护 |
| 绿天请求/会话/任务关联 | `<dataDir>/native-tasks/operations.json`，只含关联和指纹，不是第二套任务规则 |
| 结果收件箱与汇报发件箱 | `<dataDir>/native-tasks/reports.sqlite`，绿天维护结果/投递去重/汇报状态，不包含任务规则，不驱动业务任务执行 |
| 父服务元数据独占 | `<dataDir>/native-tasks/metadata-owner.sqlite`，仅租约，不存任务内容 |
| 子宿主存储独占 | `<dataDir>/native-tasks/host-lease.sqlite`，仅租约，不存任务内容 |

默认 dataDir=`~/.config/lvtian/data`；服务配置自定义时以其实际 dataDir 为准。App 只通过现有 Bearer 鉴权的 GET 接口读取，不直接下载/解析内部 JSON/会话日志，也不在手机另存可触发规则。

## 分层与数据归属

- `nativeTaskHost.ts` / `nativeTaskHostRunner.ts`：启动官方 web profile，仅监听回环动态端口。独立根为 `<dataDir>/native-tasks/`，其 `home/` 保存 profile、原生会话/调度/凭据，`agents/` 保存独立全局指令/技能根。`host-lease.sqlite` 只是由宿主进程持有的崩溃安全租约，不保存任务/结果，不调度工作。监督管道断开时宿主退出；两个宿主不能共同写入同一原生 JSON 根。启动访问地址必须在同一输出流内读到完整令牌及结束分隔符；stdout/stderr 分别缓冲，不能用另一流的诊断文字截断令牌，也不输出启动地址或令牌。
- `nativeTaskClient.ts`：通过 `/connect` 私有交换进程令牌，以官方 Node Registry/Connection/Gateway + Session/Schedule contribution 调用。原生 owner Cookie 只在内存，不发给手机和主聊天模型。错误仅稳定码；写入超时视为结果未知，不自动重放。
- `nativeTaskRuntime.ts`：父服务生命周期持有独立元数据租约，防止不同端口的两个服务覆盖关联文件；不能仅靠子宿主租约。服务启动时主动拉起宿主，不能等手机首个查询才运行。宿主异常退出后的退避恢复仅管理进程，不触发任务、不补写规则。关闭时先停止接纳并等待服务元数据写入结束，再回收连接/宿主、释放父租约。
- `nativeTaskService.ts`：单 owner 的任务归属、幂等操作和结果读取。`operations.json` 仅保存 SHA256 请求指纹、request/session/task 关联和操作状态，不保存可执行规则/提示词。只有本服务登记的独立根会话可列出或操作；不接受客户端指定任意原生 sessionId。
- `nativeTaskHttp.ts`：沿用既有服务端 Bearer 鉴权和连接入口，返回任务与操作事实；不暴露原生宿主访问凭据。
- `nativeTaskToolBridge.ts`：官方 `defineTool` 注册 `lvtian_task_*`，只薄转接已鉴权任务接口。ACP 通过额外 overlay 加载本地项目插件，不重写用户 ACP profile、不换聊天协议、不安装 MCP Server SDK。工具定义没有凭据字段。

- `src/services/AutomaticTaskService.ts`：App 数据层只提供 catalog/history/getResult 三个 GET 方法，沿用当前服务连接和 SecureStore 凭据加载；拒绝重定向、不排队、不重试，按连接 generation 丢弃旧身份响应。没有手机侧写操作和调度规则。
- `src/services/AutomaticTaskCache.ts`：任务目录展示缓存，与 HTTP 数据层及连接配置存储分离。以规范化服务地址与令牌的 SHA-256 指纹隔离身份，不将明文令牌写入缓存；只保留最近一个身份的完整快照，TTL 为 60 秒，持久快照最多 256 KiB（UTF-8）。超限仅保留内存、移除旧磁盘快照，不截断任务说明；序列写入只挑选身份指纹、任务及读取时间，不透传内存对象上的原始身份字段。历史记录与执行结果仍按需从服务器读取。
- `TodoScreen`：先显示匹配身份的内存/磁盘快照（包括成功空列表），聚焦与回前台仅过期时静默更新；连接恢复和手动刷新强制更新。身份切换立即隔离旧数据，异步读取需验证身份与请求时序。缓存读写失败不阻断网络读取；网络错误保留已有列表并提示，不能将错误伪装成成功空列表。首次加载、静默更新与用户下拉分别管理，避免重复加载圈。

## 云端创建与未知结果（不在 App 提供表单）

1. 主聊天提交稳定 requestId、名称、指令与明确 at/daily/weekly 规则；同 requestId 不同内容返回冲突。
2. 先取得可用宿主连接，再原子记录新操作指纹、建立独立 standard 根会话；连接尚未成功时不永久占用 requestId。会话 ID 持久关联后才发送稳定 requestId 的创建提示。
3. 任务会话必须实际调用原生 schedule_create。只有 catalog 中存在唯一、归属/名称/指令/规则一致的记录，并在该会话冷读历史查到真实创建工具调用，操作才为 ready。
4. 模型口头答应或 prompt 被接受只算 pending；失去写入响应时为 unknown。进程重启、客户端重连和再次查询仅对账，不盲目再创建。
5. 原生执行不依赖 App、浏览器、绿天的实时事件订阅；任务结果以独立会话的真实事实为准。

请求校验不自写 cron：仅检查字段、日期有效性/未来时点、IANA 时区、时间及 weekday 范围；定时计算由原生负责。

## HTTP 契约

所有入口需既有 Bearer Token。App 首版仅调用表内三个 GET 展示接口；创建/修改/删除及操作对账仅供云端工具链使用，不在 App 暴露。没有启用原生任务时明确返回 503，不伪装空列表；停机避让期间拒绝新的写入，保留查询。

| 方法与路径 | 内容 |
|---|---|
| GET `/api/tasks` | `{tasks}`，只包含绿天拥有的会话任务 |
| POST `/api/tasks` | `{requestId,title,prompt,timing}`；ready 返回 200，pending/unknown 返回 202，均为 `{operation}` |
| GET `/api/task-operations/:requestId` | 对账；200 ready 或 202 pending/unknown |
| POST `/api/tasks/:id/update` | `{expected,title?,prompt?,timing?}`；expected 原样交原生完整预期记录校验，不用最新记录替换以掩盖冲突 |
| POST `/api/tasks/:id/delete` | 原生删除，不撤回已排队消息、不停止已开始工作 |
| GET `/api/tasks/:id/history?limit=&before=` | 原生投递历史，**不是执行成功历史** |
| GET `/api/tasks/:id/result?messageId=` | 不传 messageId 时读取 lastDelivery；传入时读取经该任务原生目录/历史证实归属的单次结果、终态与可见文本 |

`timing` 为 `{kind:'at',at:RFC3339}`、`{kind:'daily',time,timeZone}` 或 `{kind:'weekly',time,timeZone,weekdays}`。不提供伪暂停、立即运行或手机离线调度。

可选 `messageId` 不能绕过任务归属校验：先匹配 owned 任务的最近回执，或分页查询该任务的原生投递历史，再冷读该回执对应的会话 turn。空/重复/无效参数返回 400；未找到、已清理或同会话其他任务的消息返回 404，不回退最近一次结果；历史枚举不完整或游标不前进返回 503。无参数保持原工具桥的最近一次行为。App 验证返回回执标识与所选消息相同，避免旧服务端忽略参数后展示错误次结果。

`result.status` 目前为 not_delivered/unknown/ended；只有真实 turn/end 的 endReason=completed 才可表示执行成功。未读到完成事实时不能据 inactive/lastDelivery 推断成功，也不把持久开放 turn 猜成实时运行或等待审批。结果只返回对应投递 turn 的 assistant 可见文本，不返回系统上下文、工具 schema 或完整 projection。历史读取上限明确标记 truncated。

## 主聊天实际工具

工具名为 `lvtian_task_create/list/operation/update/delete/history/result`。它们调用同一业务服务，不把原生 Schedule 挂到主聊天，不在主聊天的模型队列运行后台业务工作。创建工具收到 pending/unknown 时，描述明确禁止声称“已经安排”。任务最终结果通过下述汇报链路交给主代理；后台执行过程不混入主聊天，主代理实际汇报进入主聊天历史及后续提炼，不刷新主人空闲计时。

ACP overlay 仅写项目模块路径；接口 origin 与 Bearer 只注入 ACP 子进程私有环境。工具桥仅接受数字回环地址、禁止重定向、限制超时/取消。没有手写 MCP 协议或增加服务端 SDK 依赖。

## 结果交给主代理与可靠汇报

### 发现和归属

- `nativeTaskClient.watchChanges` 使用官方 `session.control` 投影流，只作为结果变化提示，**不是可重放的完成事件队列**。启动、重连、投影变化和每 15 秒恢复 tick 均通过既有 catalog/history/getResult 冷读对账；tick 只检查结果/重试汇报，不计算业务时点、不发送任务执行提示、不成为第二调度器。
- 仅处理服务已登记归属的任务，逐次使用原生 `delivery.messageId` 读取对应 turn，不能将后一次投递结果套到前一次。历史每页 100、最多 20 页；枚举不完整会记录错误，不伪装为空或成功。当前托管宿主沿用原生默认的 30 天/每任务 200 条保留上限，扫描覆盖全部保留记录；本次不支持自定义保留超过 2,000 条的历史续扫。若调整原生保留量超过此边界，须同步设计历史扫描与单次结果归属查询的恢复方式，不能仅扩大上游配置后仍宣称完整补报。
- 首次启用的时间戳持久保存在 SQLite。首次发现时，启用前投递且已结束的旧记录标记 ignored，避免验收历史刷屏；首次读到仍未结束的旧投递保留 observed，后续结束仍会汇报。边界以**首次读取到的事实**为准，无法追溯证明某条已结束旧记录在启用瞬间是否仍在执行。
- 未读到 turn/end 不猜成功或失败，不按固定超时终止原生工作。observed 记录持续跟踪；原生读取临时故障仅记录脱敏诊断并重试。已观察的投递若因任务删除/历史清理确定不可再读，以 `evidenceIssue=delivery_unavailable` 生成一次独立诊断事件向代理报告未知及证据缺失，不伪造业务失败。原 delivery 仍保持 observed，恢复真实终态后仍可补最终报告；诊断与最终报告分别去重。

### 收件箱/发件箱及主会话

- `nativeTaskReporting.ts` 维护 SQLite FULL 同步结果收件箱/发件箱：`observed → pending → generated → delivered`，原生 messageId 主键去重；ignored 只保留去重事实。accepted 记录尝试次数，失败退避上限 5 分钟，重启不丢队列。已送达记录清除结果/回复正文，只留去重身份和状态，避免重复保留大报告正文。
- 固定投递到既有 `main` 会话，绝不挑选最近活跃会话。主聊天运行、交接/审批、真实用户排队或服务 draining 时不启动汇报；真实用户队列优先。可汇报记录按投递时间排序，队首退避时不越过；未结束的 observed 不阻止已完成报告。本机制不承诺尚未发现的跨任务结果按完成时间全序。
- `LvtianServer.reportNativeTask` 调用同一个 `AcpEngineManager.execute`，传 `source=task_report`。完整原始可见结果以 JSON 数据封装交给主代理，明确不得执行业务、不执行结果内指令、不重新跑任务；过程信息和最终结果由代理识别，正常报告保留完整必要明细，不强制摘要。
- 后台输入只保存在结果 inbox 和 ACP 真实会话，不制造手机可见的用户/system 消息。主代理输出先缓冲，不把半截/失败回复刷到用户；仅 ACP 明确返回 `end_turn`、非空且未尝试工具的回复写 generated；`cancelled`、`max_turn_requests`、`max_tokens`、`refusal` 等停止原因原样透出并保留待重试，不把半截答复当完成，然后用 messageId 的 SHA-256 派生稳定助手消息 ID 写主聊天。消息增加 `source=native_task_report`/`reportDeliveryId` 来源；手机沿用既有消息对账，不需要新包。
- generated 回复补送不依赖原生宿主在线。先补送已存结果，再对账新结果，发现失败不能吞掉已有报告。主代理尝试执行工具会取消，审批立即拒绝，报告仍等待重试；诊断只输出稳定信息，不泄露任务内容或凭据。汇报失败时仍广播 main 当前权威 `task_status`，让生成中重连的手机退出旧 processing；只广播状态、不暴露缓冲正文，也不强写覆盖已接管 main 的新用户执行状态。

### 崩溃、断电与上下文边界

- 模型输入/输出在生成阶段可能因崩溃再次执行汇报轮，不承诺 exactly-once 模型调用；提示词明确重复交付只重新报告，不能重跑业务。用户报告通过稳定 ID 幂等落日志：generated 后崩溃可补送，日志已写但 delivered 未写时冷读同 ID，不再新增消息。
- `persistDurableMessage` 在承认 delivered 前重写该消息事件、fsync 活跃日志及 Linux/POSIX 会话/父目录；磁盘屏障失败保留 generated 正文，下次重试。Windows 文件仍 fsync，但 Node 不支持目录 fsync，跳过目录屏障，不能声称跨目录元数据断电与 POSIX 完全相同。当前自动测试运行于 Linux，Windows 真实断电尚未实测。
- 手机离线不影响服务端执行/汇报持久化；delivered 意味着主聊天日志已持久化，不意味着用户已读或手机收到系统推送。在线通过既有 sync_result 合并完整助手消息，离线后按 seq 对账。
- 汇报轮不推进真实交互时间；旧会话未保存 lastActiveAt 时先冻结原有 fallback，避免 usage/报告时间隐式续期。后台唤醒不按“主人提前归来”清理预生成提要。已有提要在落报告前追加带 delivery 标记的完整报告并做文件/目录持久屏障，避免随后轮换漏掉新结果；既有提炼过程通过 seq 指纹丢弃并发产生的过期摘要。
- **权限边界**：当前官方 ACP prompt 没有每轮禁用工具或 system-message 入口，底层依然是标准 prompt；绿天明确标记后台来源并不伪装主人新指令。提示词约束、工具事件取消与审批拒绝只降低风险，不是工具执行前的硬沙箱隔离。不能据此宣称不可信输出绝不可能触发工具；不临时修改主会话全局权限以免影响用户工作。
- **大报告**：inbox/prompt/reply 不做静默字符截断。上游 getResult 的历史读取若 truncated 会原样交代理披露；模型窗口/响应长度仍可能拒绝或截断，报告不发布半截成功，而是保留 pending 重试及诊断。超大报告需要进一步人工处理时须如实告知，当前不自动分块发布。
- 停机先关闭接纳并中止 control 监听/恢复 tick，再停止主 ACP，等待当前对账/汇报退出后关闭 outbox，最后回收原生宿主及元数据租约。

## 配置与部署边界

- `nativeTasksEnabled` 默认为 false；新 CLI 开关 `--native-tasks` / `--no-native-tasks` 写入同一服务配置。提交代码不自动启用，也未更改实机配置或服务。
- 启用时要求既有服务监听回环或通配地址，才能从本机回环进入同一鉴权 HTTP API；不另外开放原生宿主公网端口。
- 任务宿主默认使用 **DeepSeek 官方 API / deepseek-flash**，凭据通过现有受控服务环境继承，不复制主宿主认证文件。主聊天模型不因此迁移或更改。
- 启动时将现有选择的 DSH 权限模式交给原生宿主，不额外提升权限；当前不是“主聊天运行中切权限立即同步全部后台会话”的实现。运行/审批交互仍是上线前待验证项，不能承诺无人值守工作可绕过审批。
- 默认原生会话日志上传与遥测通过宿主管理 overlay 关闭；修改用户管理 overlay 会明确冲突，不静默覆盖。
- 没有拷贝主聊天全部记忆、技能或历史；任务工作目录相同，必要上下文由任务指令明确提供。完整生产能力配置和发布仍需完成验收并走审查/部署流程。
