# 绿天原生定时任务接入规划与范围调整

日期：2026-10-26

状态：2026-10-26 用户已确认云端任务方案，并将 App 首版收窄为只读展示。最小原生离线/重启执行、真实主聊天工具创建、原生管理操作均已运行验证；App 只读数据接入和页面已有实现及本地测试。首版不做管理表单、完成停止或主聊天通知。生产服务未变更；提交/审查须按统一 PR 流程核验，不能用本地测试代替。现行接口见 [自动任务架构与接口](自动任务架构与接口.md)，实测细节见 [验证记录](原生定时任务验证记录.md)。

## 最新首版范围（2026-10-26 用户明确收窄）

首版只解决云端任务存储与 App 只读展示：规则文件为 `<dataDir>/native-tasks/home/storages/schedule.json`，执行会话和结果在同根 `sessions/`。App 仅调用 GET 查询，不做新建/编辑/删除/完成停止，不做主聊天结果通知或系统推送。现行实现和界面范围分别以 [模块说明](自动任务架构与接口.md)、[只读展示说明](界面交互稿.md) 为准。

下方保留原分阶段扩展规划用于追溯；其中管理表单、通知及状态细分不再是首版交付要求，不据此扩大实现。

## 一、推荐结论

优先复用云端 DeepSeek Harness 原生 Schedule、会话控制与持久化，绿天只补接入、产品展示和结果交付，不自建 cron 引擎，不用手机计时或唤起任务。

先完成一个完全在云端运行的最小验证，再接入正式服务端与 App。现有主聊天暂保留 ACP；原生后台宿主仅承接任务。双链路是有明确边界的分阶段接入，不预设为长期架构；是否统一主聊天接口，待验证后另行决定，不与本次定时能力绑在一起改造。

正式上线之前必须同时满足：手机断网或关闭不影响到期执行；任务规则重启可恢复；定时工作不进入主聊天执行上下文；任务结果可查询、断线后可补读。

## 二、不可改变的边界

1. **云端负责全部任务逻辑**：规则保存、时间计算、到期触发、AI 执行、状态与结果保存均在云端。手机只提交管理请求并展示云端事实。
2. **原生服务是唯一调度源**：不另建一份能独立触发执行的任务表，不自己计算权威下一次运行时间，不用系统 cron 平行触发同一任务。App 的倒计时只用于展示。
3. **主聊天与任务会话隔离**：任务使用独立普通根会话，不使用主聊天，也不能用受原生限制的被委派 subagent 会话代替。
4. **独立会话不等于每次新建**：首版先验证每个定时任务绑定一个独立会话、每次到期在该会话运行；不要求原生调度器每次创建新会话。长期任务会话的增长与压缩沿用底层能力，先测清再决定是否需要额外策略。
5. **不复制整个主聊天上下文**：只向任务会话提供必要指令、工作目录、资料位置及明确权限；不能为了任务创建把主聊天全部历史转发过去。
6. **保持当前主聊天稳定**：不更换现有聊天协议、历史数据或服务配置，不用调度开发顺带重写 ACP 管理与会话轮换。
7. **上线前另行确认**：本稿只规划；代码修改、服务配置、进程守护、原生宿主上线与发布分别按项目流程进行，不在规划阶段执行。

## 三、已查证能力与待验证边界

| 项目 | 已查证内容 | 接入含义 |
|---|---|---|
| 原生 Schedule | 支持 after、at、固定间隔、daily、weekly、五字段 cron | 复用时间解析、时区、调度与持久化，不自己实现 |
| 宿主依赖 | Schedule 需要 Session controller、storage-domain 和会话持久化；不能在纯 ACP/headless 组合里单独挂载 | 必须验证一个具备这些服务的云端原生宿主 |
| 远程管理 | 生成的 Schedule Remote 只有 catalog、list、history、update、delete | 不把内部 create 方法当成现有公网 API |
| 原生创建 | 内部 ScheduleService.create 存在；官方 Web 任务页通过新建会话、由模型调用 schedule_create 创建 | 首选沿用原生创建工具，并以持久化目录回读确认成功 |
| 会话归属 | 任务绑定原会话；被委派子会话不允许创建和正常投递 | 创建时绑定独立普通根会话 |
| 投递记录 | lastDelivery/history 证明持久收件箱投递，不证明模型执行完成；默认历史按30天/200条裁剪 | 任务执行与成果须读取真实会话状态和结果，不承诺永久完整历史 |
| 失败与崩溃 | 恢复、入队或持久化失败没有自动重试定时器；收件箱入队与任务记录写入非原子，崩溃可能重复投递 | 单独验证失败后恢复与重复风险，不宣传自动重试或恰好一次执行 |
| 接口与权限 | Schedule 会话绑定检查不是调用者授权；catalog 为宿主级目录 | 绿天适配层必须校验可访问的任务/会话范围，不向任意客户端直接透传全部目录 |
| 通知可靠性 | schedule/changed 是失效通知；普通事件不承诺断线回放 | 连接恢复必须重新读取权威目录，不能只靠事件 |
| JSON 存储 | 没有跨进程写锁，同文件可能发生后完成写入覆盖 | 新宿主必须独占其调度、会话和配置写入目录 |
| 原生 todo_write | 是单一 Agent 会话的执行步骤清单，整表替换 | 不作为跨会话个人待办库或定时任务库 |
| 当前 App | TodoScreen 仍为占位页；现有服务端无用户任务调度服务 | 可以新增任务展示，但不能把占位页替换就说调度已完成 |

以上接口结论以所安装版本为准。升级 Harness 后须重新核对，不凭本稿假定接口永远不变。

## 四、目标职责与数据流

### 4.1 组件职责

- **手机 App**：使用现有绿天连接入口提交任务设置，展示权威任务目录、规则、下次运行、投递记录、实际执行状态与结果。没有后台计时器，没有对云端宿主的直接凭证依赖。
- **绿天服务端适配层**：校验身份与请求，连接原生 Remote，建立任务与独立会话的对应关系，转换返回数据，恢复断线查询，交付结果。它不是第二个调度器。
- **原生任务宿主**：在云端常驻，加载 Schedule 及其依赖。计算到期时点、保存规则、恢复任务会话、投递指令、运行模型与工具。
- **现有 ACP 主聊天链路**：继续负责当前主聊天。后台任务不通过这条聊天执行队列运行，不刷新主聊天空闲时间。

手机提交设置后，任务运行数据流为：原生云端 Schedule 到期 → 恢复独立任务会话 → 执行 → 保存实际结果 → 绿天服务端读取或订阅并保存交付关联 → App 在线展示或重连后补读。到期后这一链路不能依赖手机发起任何请求。

### 4.2 创建方式

首版优先采用官方现有路径：在任务宿主建立独立普通根会话，将已明确的标题、指令、时间和时区交给会话，通过 schedule_create 工具创建。只有目录回读中存在相应任务、绑定与规则均正确，才返回“已安排”的业务结果；模型仅口头答应不算成功。

暂不设计不存在的原生 HTTP 创建接口。若后续需要完全不经过模型的表单创建，再评估极薄的 Host 扩展调用原生 ScheduleService.create；这属于新增接入能力，须另行确认，不能修改上游包源码，更不能趁机另写调度器。

创建超时或连接中断时，先对账确定是否已落盘，不盲目重试创建。创建请求与原生任务标识的关联是否需要本地持久记录，在验证阶段确定；允许保存操作关联元数据，不允许复制一套权威定时规则。

主聊天里自然语言交办任务需要有真实的跨宿主创建入口；若首版纳入，须增加受控的服务端工具桥接并进行端到端验证，不能只在提示词中声称已具备 schedule 工具。第一阶段不默认该桥接已经存在。

### 4.3 结果交付

- 任务详情能够打开其执行会话与实际输出，作为最基本且可追溯的交付。
- 主聊天只追加最终结果通知或结果入口，不追加任务的用户指令、思考和工具过程，不调用主聊天模型来转述，不更改 lastActiveAt。
- 当前主聊天在缺少 lastActiveAt 时会回退到最后消息时间。仅仅不调用模型还不足以保证通知“不续命”：必须覆盖新会话/旧数据的回退路径，并验证通知不进入记忆提炼、挤占用户对话锚点，不改变任务状态或用量。
- 结果通知需要稳定关联标识，支持服务端重启、App 重连后的补读和去重。关联优先复用底层会话、投递消息和真实执行事件标识；具体映射先验证，不自创第二份执行日志。
- 界面内可查结果与操作系统推送是两项能力。首版不承诺手机杀进程后弹系统通知；如需要，另行设计推送通道，不让任务执行依赖推送成功。

## 五、产品范围

### 5.1 “待办”统一入口，数据语义保持区分

产品上可以继续使用“待办”标签呈现用户交办的事项，但首版先接通自动任务，不强行把人工事项或模型内部执行步骤变成 Schedule。

- **人工待办**：由人完成，可有日期，但日期不自动代表定时执行。
- **自动任务**：有明确执行指令与运行时间，由云端自动唤起。
- **内部执行步骤**：原生 todo_write 计划，附属于某次工作，不默认进入长期事项列表。

人工待办的长期存储与 Google Tasks 接入不在本次接通原生 Schedule 的范围内。

### 5.2 推荐首版能力

- 创建自动任务：一次性、每天、每周；明确显示任务时区，默认建议 Asia/Shanghai，但创建前展示可确认的实际规则。
- 查看任务名称、指令、规则、下一次运行及绑定会话。
- 修改原生允许修改的任务名称、指令和时间；回读确认保存状态。
- 删除任务前确认，并明确原生删除会移除调度规则与投递历史，不等于停止已经投递或正在执行的工作。
- 查看原生投递记录、真实执行状态及结果入口。
- 执行过程中需要审批时，正确呈现等待授权，而不是错误地显示任务成功。

固定间隔、cron、自定义表单、暂停/恢复、立即运行、人工待办、Google Tasks、系统推送和复杂筛选不是首版默认承诺。底层支持的高级规则可在后续扩展；对“暂停”等未确认存在的原生接口，不伪造按钮或通过删建任务假装原地暂停。

### 5.3 状态展示必须分层

- **规则状态**：原生 active/inactive、下一次目标时间。
- **投递状态**：本次到期指令是否已进入持久会话收件箱。
- **执行状态**：真实执行中的排队、运行、等待审批、结束或失败，依据会话事实映射，不能由投递回执推断。
- **交付状态**：结果是否已保存并对 App 可读；与设备是否实际查看分开。

原生 inactive 尤其不能直接翻译成“工作已完成”。

## 六、分阶段实施与准入门槛

### 阶段 0：隔离环境中的原生能力验证

不先改 App，不改现有服务，不建立生产定时任务。

1. 使用现有依赖启动独立原生任务宿主，独立存储 root/profile/会话数据，凭据采用受控引用，不复制或打印具体密钥。
2. 只监听本机回环接口，绿天服务端访问；不额外向公网暴露原生宿主、管理 cookie 或 owner 凭证。
3. 验证认证后的 Node Remote 调用、目录查询、独立根会话创建、实际 schedule_create 创建及任务回读。
4. 关闭所有 App/浏览器连接，验证真正到期投递并执行，而非仅在有前端在线时才工作。
5. 在隔离宿主中验证重启恢复、冷会话恢复及错过周期的补发规则。
6. 验证执行状态与结果的读取链路，以及审批无前端在线时的准确行为。
7. 记录宿主资源占用和真实接入代码量，评估双链路成本是否可接受；同时以现有主聊天的恢复、附件、审批、停止、排队、权限切换和空闲轮换用例对照原生 Remote 覆盖能力。阶段0只比较、不迁移主聊天；阶段1开工前明确采用有退出条件的双链路，还是另行立项统一宿主。
8. 确认新宿主的模型路由、凭据引用、preset、Skill、记忆注入与权限配置分别由谁管理。现有 dshConfigManager 只维护 ACP profile，不能假设它自然覆盖任务宿主。使用不同端口并不等于已隔离配置和数据。

产出：可重复运行的验证脚本与结果说明、实际接口映射、存储隔离配置草案、尚不满足的能力列表。验证结果为“可行”之前，不将规划接口写成现有实现。

**停止条件**：原生宿主必须有浏览器在线才能运行、需要改上游核心调度才能使用、数据隔离不成立、认证依赖不可维护的内部补丁，或根本无法可靠观察任务结果。出现这些情况先汇报事实和取舍，不自行转向自建调度器或整体迁移主聊天。

### 阶段 1：云端服务端接入

验证通过并确认方案后，在独立任务工作树实施：

- 增加原生任务宿主生命周期与连接适配，清晰区分“宿主不可用”“权限不足”“任务不存在”“请求结果未知”。
- 接入任务目录、修改、删除、投递历史与创建路径；不重复保存可驱动执行的规则。
- 根据真实事件建立执行结果关联；恢复后重新读取基线，不只等待实时通知。
- 后台任务与主聊天执行队列、会话存储、停止控制、空闲计时隔离。
- 权限默认继承受控策略；不为了无人值守一律开启完全权限。需要审批则等待或按已明确的策略终止，不能无声放行。
- 增加服务端集成测试，验证重复请求、重启、断线、结果去重与越权访问。

产出：云端端到端能力、协议定义、自动测试和原生宿主部署草案。本阶段可通过测试客户端验收，仍不要求手机参与触发。

### 阶段 2：App“待办”自动任务入口

- 用云端权威数据替换当前 TodoScreen 占位内容。
- 增加列表、详情、创建入口、修改/删除确认、执行结果与等待审批展示。
- App 只通过现有绿天服务端鉴权链路访问，不直接持有原生宿主凭证。
- 创建/修改在离线时不得显示“已安排”；首版不暗中建立一套手机端离线调度规则。
- 错误与查询中状态明确区分，不把接口失败显示成空列表，不把接收回执显示成完成。
- 新界面文案先确认，再实现中文与英文对应资源；做窄屏、大字体和断线重连真机验收。

产出：可供用户管理和查阅的 App 界面、界面测试和人工验收清单。

### 阶段 3：受控上线

- 先展示完整宿主配置与守护部署文件，再按现行授权流程部署；不提前重启现有聊天服务。
- 用一个低风险测试任务验证上线后的运行、结果交付与一次重启恢复，再转入正式任务。
- 监控任务逾期、投递失败、模型执行失败与审批等待；日志只记录必要标识和错误，不打印凭证。
- 分别核对服务端部署与 App 发布条件，不能把 App OTA 成功当作云端宿主已部署。
- 故障回退须明确停止新任务宿主的投递并展示未运行状态，保留其数据；不能只撤掉 App 页面却让后台重复执行。主聊天原 ACP 链路不受此回退影响。

## 七、最小验收矩阵

| 场景 | 必须观察到的结果 |
|---|---|
| 创建一次性任务 | 工具返回与权威目录回读一致，时间、时区、任务会话均准确 |
| 手机断网、App 关闭、无浏览器连接 | 到期仍由云端投递并产生真实执行结果 |
| 每天/每周任务 | 下一次目标遵循原生规则与显式时区，不靠手机时区重算 |
| 宿主重启 | 规则与会话绑定恢复；不丢任务，不因 App 重连重建一份任务 |
| 停机跨过多个周期 | 行为与原生“只补最近一次错过时点”等实际语义一致，不擅自补跑所有历史 |
| 会话冷却 | 到期可由原生宿主恢复独立根会话 |
| 创建或更新超时 | 显示结果待确认并对账，不盲目重复写入 |
| 修改冲突 | 遵循原生完整预期记录校验，保留待确认输入，不悄悄覆盖其他改动 |
| 删除 | 规则及历史按原生语义移除，不承诺撤回已入队消息或停止执行 |
| 投递成功、模型随后失败 | 显示投递已发生与执行失败，不显示“任务成功完成” |
| 权限不足/需要审批 | 任务不越权，App可查等待或失败原因；手机不在线也不自动绕过审批 |
| 下一周期到达时前一轮仍在执行 | 观察原生会话收件箱与并发行为，不误判运行轮次，不另加并行执行器绕开原生规则 |
| 任务与主聊天同时工作 | 不占用主聊天执行队列，不把后台工具过程塞入主聊天 |
| 最终结果通知与重启补读 | 一个实际结果不重复展示；有/无lastActiveAt均不触发主聊天模型、不延长空闲计时、不污染记忆提炼 |
| 多客户端访问或越权标识 | 未授权客户端不能列出、修改或删除其他会话的任务，错误不泄漏任务内容 |
| 原生宿主断连 | 查询明确失败，恢复后回读目录与结果，而非永远等待丢失事件 |
| 两个宿主的数据目录 | 不发生共同写入同一 schedule JSON/会话文件或配置文件 |

原生持久投递不自动保证外部副作用“恰好一次”。涉及发邮件、修改业务数据等任务，仍须遵循操作授权，并在具体任务层验证幂等或采取确认机制；不把这个问题扩大成首版自建通用重试引擎。
