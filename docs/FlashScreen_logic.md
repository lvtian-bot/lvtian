# 闪念笔记页 (FlashScreen) 业务逻辑执行流程详解

本文档按照代码实际运行的先后顺序，详细拆解了闪念笔记页面的完整业务逻辑。

---

## 1. 阶段一：页面初始化 (loadInitialData)

当用户打开或切换到本页面时，主组件触发 `useFocusEffect` 钩子，随即调用核心初始化函数 `loadInitialData`。此时，系统立即执行以下操作：

1.  **设置刷新状态**：
    系统将界面变量 `isRefreshing` 设为真，UI 界面顶部开始显示下拉刷新指示器（Spinner）。

2.  **启动后台历史同步任务（分支 A）**：
    *   系统发起对 `flashNoteService.syncHistoryFiles` 的调用。
    *   **关键逻辑**：这是一个“异步非阻塞”调用。主程序**不会**等待该任务完成，而是立即继续向下执行步骤 3。该任务在后台独立运行（详见阶段二）。

3.  **加载本地文件列表（分支 B）**：
    *   系统调用 `loadFilePaths`，从本地文件系统读取所有闪念笔记的文件路径。
    *   系统等待读取结果返回。

4.  **加载并解析首个文件**：
    *   系统读取列表中的第一个文件（通常是当前的主文件）。
    *   系统将文件内容解析为笔记对象数组。

5.  **渲染数据并结束刷新**：
    *   系统更新 `notes` 状态变量，界面瞬间显示出笔记列表。
    *   系统将 `isRefreshing` 设为假，隐藏刷新指示器。

---

## 2. 阶段二：后台历史同步 (syncHistoryFiles)

这是在阶段一第 2 步中启动的后台任务，其运行逻辑封装在 Service 层中：

1.  **网络环境自检（熔断机制）**：
    *   程序首先调用 `NetInfo` 检查当前网络连接状态。
    *   **判断**：如果网络状态为断开（离线）：
        *   **执行**：程序打印一条“Offline”日志，并立即**终止函数执行**（Return）。
        *   **结果**：后续所有云端请求都被物理拦截，确保不会引发崩溃。

2.  **云服务配置检查**：
    *   **判断**：检查 `cloudService` 是否已配置 Key 和 Secret。
    *   **执行**：若未配置，立即终止执行。

3.  **获取云端列表**：
    *   程序向云端发起请求，获取指定目录下的所有文件清单。

4.  **差异比对与下载**：
    *   程序遍历云端清单，筛选出本地不存在的历史归档文件。
    *   对每一个缺失的文件，调用 `syncService` 执行下载操作。

5.  **完成回调**：
    *   一旦所有下载完成，程序触发回调，通知 UI 再次执行 `loadFilePaths`，以便将新下载的历史文件显示在列表中。

---

## 3. 阶段三：实时同步监控 (useCloudSync)

在页面加载完毕后，`useCloudSync` 钩子函数启动，开始持续监控主文件的状态：

1.  **状态检查入口 (checkSync)**：
    *   钩子函数调用 `syncService.checkSyncStatus` 方法。

2.  **网络与配置复检**：
    *   **判断**：再次检查 `NetInfo` 网络状态。
    *   **执行**：若离线，直接返回状态值 `'offline'`。UI 顶部随之显示黄色离线横幅。

3.  **哈希 (Hash) 比对逻辑**：
    *   若在线，程序分别获取三个哈希值：**本地哈希**、**影子哈希**（上次同步的快照）、**云端哈希**。
    *   **判断 A**：`本地哈希` 等于 `云端哈希`。
        *   **结果**：返回状态 `'synced'`。UI 显示“云朵打钩”图标。
    *   **判断 B**：`本地哈希` 等于 `影子哈希`，但 `云端哈希` 变了。
        *   **结果**：判定为“云端更新”。程序自动触发下载覆盖本地，UI 列表自动刷新。
    *   **判断 C**：`云端哈希` 等于 `影子哈希`，但 `本地哈希` 变了。
        *   **结果**：判定为“本地更新”。程序自动触发上传覆盖云端。
    *   **判断 D**：三者都不一样。
        *   **结果**：判定为“双向冲突”。返回状态 `'conflict'` 以及类型 `'bidirectional'`。

---

## 4. 阶段四：冲突智能合并 (Smart Merge)

当阶段三判定为“双向冲突”时，根据当前配置，程序可能进入智能合并流程：

1.  **获取三路文本**：
    *   程序分别读取：**Base**（影子文件内容）、**Mine**（本地文件内容）、**Theirs**（下载云端文件内容）。

2.  **执行算法合并**：
    *   调用 `diff-match-patch` 算法尝试合并文本。

3.  **合并结果判定**：
    *   **分支 A：合并成功**
        *   程序将合并后的文本写入本地文件。
        *   程序立即将合并后的文本上传至云端。
        *   程序更新影子文件。
        *   **UI 反应**：状态自动变回 `'synced'`，用户无感知。
    *   **分支 B：合并失败**
        *   程序保持 `'conflict'` 状态。
        *   **UI 反应**：页面顶部弹出橙色横幅“本地和云端已同时修改”，并提供“使用云端”、“保存副本”等手动解决按钮。
