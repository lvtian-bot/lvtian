# 绿天（Lvtian）技术架构

> 全貌文档：产品形态、分层架构、核心数据链路、状态设计与工程约定。排查或开发时先在此定位所属领域，再进入 `docs/` 对应子目录查阅专项设计与问题记录。

---

## 1. 产品形态与核心技术栈

绿天（Lvtian）是一款基于 **DeepSeek Harness** 的**个人 AI 代理（Personal AI Agent）**系统。由常驻运行的独立服务端（`server/`）承载代理执行中枢与工具调用能力，并由基于 **React Native (Expo)** 构建的移动端作为随身任务交互控制台与审批中枢。

| 层面 | 技术选型 | 说明 |
|------|---------|------|
| **框架** | React Native 0.88.0 + Expo SDK 58 (Prebuild CNG) | 原生层由 `app.config.js` 与插件定制生成，禁止直接改动 `android/` |
| **语言** | TypeScript 6.x (严格模式) | 严禁使用 `any`，全链路类型安全 |
| **状态管理** | Zustand 5.x | 轻量模块化 Store，内存态 + AsyncStorage / SecureStore 持久化 |
| **文件系统** | `expo-file-system` | 唯一通过 `FileSystemService` 封装，适配 Android Scoped Storage |
| **编辑器** | CodeMirror 6 + WebView 托管 | 源码位于 `src/editor-web/`，经 Vite 打包注入原生 WebView |
| **同步核心** | 自研三阶段同步 + 三路合并算法 + 影子文件系统 | 支持 412 乐观锁冲突救援、逐文件队列流转与离线容错 |
| **云端协议** | WebDAV (坚果云等；原腾讯云 COS 已退役) | 基于 `ICloudProvider` 抽象策略模式 |
| **国际化** | i18next + react-i18next | 多语言支持，启动首位加载，禁止硬编码界面文本 |

## 4. 核心数据流架构

### 4.1 云优先 + 本地加速链路
绿天坚持**云端为唯一真相来源（Single Source of Truth）**，本地文件系统作为加速读写的受控缓存：

```text
[用户发起保存]
      │
      ▼
┌──────────────┐   1. 立即写入 (保证响应)
│ 本地文件系统 │ ◄────────────────────── [Editor / FlashNote]
└──────┬───────┘
       │
       │ 2. 加入上传队列 (Write-Through)
       ▼
┌──────────────┐   3. 携带 ETag 条件上传
│ 云端对象存储 │ ◄────────────────────── [SyncService.upload]
└──────┬───────┘
       │
       ├─► [成功] ──► 更新本地 ETag 与同步基准副本 (.shadows/)
       │
       └─► [412 冲突] ──► 触发三路合并救援 (Smart Merge)
                              ├─► 合并成功: 自动二次上传，用户无感知
                              └─► 合并失败: 标记冲突，UI 弹出选项
```

### 4.2 写入链路 (Write-Through)
- 用户在编辑页或闪念输入时，首先通过 `FileSystemService` 写入本地沙盒。
- 紧接着将文件路径推入 `useSyncStore` 的上传队列。
- 上传成功后，`useFileMetadataStore` 记录最新的云端 `etag`，并将此时的内容通过 `ShadowFileService` 备份到 `.shadows/` 作为未来冲突比对的共同祖先版本。

### 4.3 读取链路 (Cache-First / 按需加载)
- **浏览列表**：优先加载 `AsyncStorage` 中的云端快照，后台静默请求云端列表拉取增量，严禁遍历本地硬盘生成目录。
- **打开文件**：点击列表项时做懒检查（Lazy Check），本地有则秒开，本地无则触发 `SyncService.performDownload` 下载后呈现。

---

### 4.4 主聊天流与历史回放
- 服务端继续按任务保存一条助手消息：`content` 存完整文字、`toolCalls` 存工具最新状态，`toolCallPositions` 只记录每个工具首次出现的正文 UTF-16 偏移。事件日志与快照共同持久化锚点。
- 移动端 `AssistantClient` → `useAssistantStore` 按实时事件记录相同位置；重连以 `sync_result` 的服务端完整消息覆盖，避免只在当前界面临时拆段。对账按服务端时间排序已受理消息，同一毫秒保持到达顺序；未受理的本地消息按原顺序置于末尾，不参与整段排序。`seq` 只作增量同步游标，会随流式更新重写，不能用于排序。`assistantMessageParts.ts` 根据锚点派生正文与工具序列；聊天页只渲染用户消息与助手正文，工具调用进入按“一次用户请求”聚合的工作记录（聊天页右上入口），由 `chatTurns.ts` 依据助手消息的 `replyTo` 归轮并派生出标题、结果摘要、完成时间与工具流水。旧历史没有 `replyTo` 时回退到到达顺序，不猜测。详见 [服务端架构与协议](服务端/服务端架构与协议.md)。

## 5. 跨模块设计模式与工程约定

1. **DRY 铁律（严禁逻辑碎片化）**：
   - 同步流转、冲突解决、文件写入逻辑**绝对禁止**散落在各个 Screen 组件中。
   - 所有文件读写必须经由 `FileSystemService`。
   - 所有云端操作必须经由 `CloudService`（操作前必须校验 `isConfigured()`）。
2. **状态管理分层**：
   - UI 组件通过 Hooks 读取 Store。
   - Services 层需要获取状态时，通过 `store.getState()` 读取，规避 React Hooks 规则约束。
3. **国际化约束**：
   - 所有用户界面文案必须通过 `i18next` 提取至 `src/locales/`，禁止直接硬编码中文字符串。
4. **应用主题配色**：
   - 应用界面颜色集中由 `src/utils/theme.ts` 的语义 Token 管理；主蓝色为 `primary=#60A5FA`，浅蓝背景为 `primaryLight=#EBF5FF`，深蓝色为 `primaryDark=#3B82F6`。
   - 聊天页用户头像、用户消息气泡和发送按钮的启用态使用 `primary`，不得通过改用深色 Token 间接加深主体蓝色。消除硬编码属于代码整理，不应改变既有配色；对比度优化须作为独立视觉变更评估。
