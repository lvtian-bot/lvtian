## 1. 产品定位

绿天是用户自行部署的长期个人 AI 助理，由独立服务端与安卓客户端组成。服务端安装在用户自己的 Windows 或 Linux 机器上，负责助理运行和数据保存；安卓客户端提供日常交流、事项跟进、内容阅读和文件访问入口。

产品以持续使用同一个助理为中心，保持简单直观的移动交互。客户端以五个固定标签组织主要能力：主聊天、闪念、待办、新闻摘要、系统文件。界面不以应用或项目管理作为主要入口。

绿天承接 MDNote 的产品位置，在原仓库上演进。青梧继续承担办公桌面客户端的职责；Windows 个人助理客户端不纳入本期交付。

## 2. 已确定的产品边界

| 事项 | 范围 |
| --- | --- |
| 客户端 | 优先交付安卓 App |
| 服务端 | 可独立安装和运行，首版覆盖 Windows 与 Linux |
| 部署模式 | 用户自行部署，不建设集中托管助理的公共云服务 |
| 助理归属 | 一个服务端实例对应一个独立助理；不同实例各自保存会话、配置、记忆和文件 |
| 同一实例访问 | 手机连接对应服务端，操作该实例中的助理和数据 |
| 主要导航 | 主聊天、闪念、待办、新闻摘要、系统文件，五个标签均保留 |
| 持续运行 | 手机关闭或断开连接不应主动终止服务端中的助理任务；实际运行以宿主机器和服务在线为前提 |
| 数据归属 | 服务端是助理业务数据的正式保存位置；闪念暂保留原 WebDAV 数据链路，手机保留必要缓存和草稿 |
| 引擎方向 | 继续以 DeepSeek Harness（dsh）为基础，不另行实现 Agent 循环 |
| 原文档同步 | 移除 COS 支持；WebDAV 收缩为闪念所需的数据链路，保留其必要同步能力 |

## 3. 核心使用场景

1. 在主聊天中持续与助理交流、安排事情，离开 App 后再次进入能够继续查看进展。
2. 助理将需要长期跟进的事项记录到待办中，事项可能由助理执行、由人执行，或双方配合完成。
3. 在新闻摘要标签集中阅读助理整理的资讯，并能够围绕摘要继续交流。
4. 在系统文件标签浏览助理所在机器上的文件，查看和获取助理产出的成果。
5. 通过闪念标签继续记录和阅读想法，暂保留现有 WebDAV 保存与同步方式；助理介入方式后续定义。

## 4. 安卓端功能需求

### 4.1 主聊天

**目标**：提供面向同一个长期助理的持续交流入口。

已确定需求：

- 主聊天是产品的主要入口，不以创建和切换大量应用或项目作为使用前提。
- 可以向助理发送消息，并查看回复、任务进展和结果。
- 助理运行不依附于手机页面是否打开；重新连接后能够恢复查看服务端中的对话和状态。
- 需要人工决策时，能够在客户端查看请求并作出回应。

建议的首版基础能力，实施前确认具体交互：

- 文本输入、流式回复、历史加载、停止当前执行。
- 以简洁方式呈现工具活动和执行结果。
- 附件上传与成果文件入口。
- 已连接、连接中、断开等状态可辨认；发送失败不得表现为已经成功。

待定项：主聊天是否始终只有一条、是否允许另开话题、语音输入范围，以及待办和摘要如何带入聊天。

### 4.2 闪念

**目标**：保留快速记录想法的独立入口。

已确定需求：

- 闪念作为五个主要标签之一保留，当前改造保留现有记录和时间线阅读能力。
- WebDAV 暂时保留，范围收缩到闪念相关文件及必要的历史记录。
- 保留闪念所需的缓存、上传、冲突处理和编辑能力，不随 COS 或旧待办清理一并移除。
- 暂不切换为调用 Web Clipper 接口；后续如调整保存链路，需单独定义记录与阅读行为。

待定项：

- 是否在现有文字记录基础上扩展图片、语音或其他分享形式。
- 是否增加提交后立即交由助理处理的能力。
- 助理如何整理、归类，以及是否将某条记录转为待办。
- 是否增加搜索或调整现有编辑、删除交互。
- 后续如替换现有同步方式，离线保存、提交与自动重试行为如何调整。

本次以保留现有闪念行为为基线，不为尚未确定的扩展能力重写闪念系统。

### 4.3 待办

**目标**：集中呈现由助理记录、维护和持续跟进的事项。

“由助理记录”和“由谁完成”是两个维度。待办可以是需要人处理的事情、助理自己的工作，也可以是双方协作的事项，不按人和 AI 强制拆成两套清单。

当前改造清理原有从闪念 Markdown 提取个人待办的专用页面和业务逻辑；助理待办仍属于产品范围。清理不得删除闪念原文中的 Checkbox 或影响闪念记录、阅读与同步，共用代码须核查调用后再处理。

| 事项示例 | 完成人或执行方 |
| --- | --- |
| 给客户打电话 | 人 |
| 整理行业新闻 | 助理 |
| 整理方案，待确认后继续处理 | 助理与人配合 |

已确定需求：

- 待办由助理记录、维护和跟进，允许包含不同执行方的事项。
- 事项需要能跨聊天轮次持续查看和跟进。
- 清单需要反映实际进展，避免把已经受理、正在处理和已经完成混为一谈。

建议的首版表达：

- 每项展示事项内容、当前进展和下一步需要谁处理。
- 保留进入相关聊天或结果的入口。
- 单次执行的内部步骤可以附属于事项，不默认全部铺入长期事项列表。
- 记录一条事项与安排自动执行分别处理，不能仅因存在一条待办就声称已经安排定时执行。

待定项：直接新建和编辑范围、完成状态如何确认、日期与提醒、周期事项、筛选方式，以及 Google Tasks 等外部工具的后续接入。

### 4.4 新闻摘要

**目标**：集中呈现助理整理、交付的资讯内容。

已确定需求：

- 新闻摘要是独立标签，内容由助理整理产出。
- 页面呈现摘要成果，不以个人手工维护的新闻收藏清单为中心。

建议的首版表达：摘要列表与正文阅读，保留原始来源入口，并能够围绕某篇摘要继续询问助理。

待定项：关注主题和来源如何设定、按需生成还是定期生成、生成频率、历史保留与搜索、通知方式，以及生成失败时如何提示。

### 4.5 系统文件

**目标**：访问助理所连接服务端机器上的文件。

已确定需求：

- 文件属于当前服务端实例；连接 VPS 时浏览该 VPS 上的文件，连接 Windows 服务端时浏览该 Windows 机器上的文件。
- 文件入口服务于查看助理工作资料和成果。
- 原笔记标签页调整为系统文件入口，默认打开所连接服务端的用户主目录；目录由服务端返回，客户端不写死 Linux 或 Windows 路径。
- 不默认将整个服务端文件系统双向复制到手机。

建议的首版基础能力：目录浏览、支持类型的文件预览、下载或系统分享，以及从聊天成果进入对应文件。

待定项：默认目录对应的服务端账户、主目录之外的可浏览范围、上传位置、首版预览类型，以及是否提供编辑、移动、重命名和删除等管理操作。默认打开主目录不等于将访问范围限定为主目录。

## 5. 客户端与服务端的配合要求

本节定义产品可见的行为边界，不指定最终网络和存储实现。

| 安卓端动作或场景 | 服务端配合要求 |
| --- | --- |
| 打开主聊天 | 提供可恢复的历史与当前运行状态 |
| 发送消息 | 明确反馈是否已受理，并将执行过程和结果返回客户端 |
| 手机断网或关闭 App | 不将客户端离线直接等同于任务取消 |
| 重新连接 | 以服务端当前状态恢复展示，不靠手机旧缓存推断任务结果 |
| 处理审批或问答 | 核对请求是否仍有效，反馈处理结果 |
| 查看待办和摘要 | 读取同一实例正式保存的数据，能够获得最新变化 |
| 访问系统文件 | 在当前实例的可访问范围内读取或传输文件 |
| 切换实例 | 使用该实例的数据，不混入另一个实例的记录和缓存 |

首版至少需要完成单实例连接。多实例同时在线、实例列表和切换界面的范围尚待确定。

## 6. 数据与同步原则

- 会话、助理配置、长期事项、摘要和服务端文件，以所属服务端实例为准。
- 安卓端的连接信息、界面偏好、缓存和未发送草稿属于客户端状态；缓存应按实例隔离。
- 闪念保留现有 WebDAV 保存与同步链路，其正式内容仍以对应 WebDAV 文件为准；当前改造不强制迁入助理服务端。
- 主聊天、助理待办、新闻摘要和系统文件通过服务端连接获取数据；闪念 WebDAV 同步不承担上述业务的数据交换。
- COS 支持退出；共享同步与文件能力仅在确认不再被保留功能使用后删除，不以删除数量作为改造目标。
- 保留现有云端内容，不因调整手机界面而删除原有文档；历史笔记是否导入另行确定。
- 连接凭据与模型凭据不得写入日志或文档，手机上的敏感凭据使用系统安全存储。
- 远程接入的网络方式、配对方式和认证交互另行设计，不在本草案中确定 Tailscale、公网入口或中继方案。

## 7. 本期范围与后续范围

### 本期产品范围

- 安卓个人助理客户端，保留五个主要标签。
- 可独立安装和运行的 Windows／Linux 服务端。
- 主聊天、执行状态、人工交互，以及客户端重连后的状态恢复。
- 按各标签进一步确定的范围，提供闪念、长期事项、新闻摘要与文件访问。

### 暂不纳入本期

- Windows 个人助理客户端与 iOS 客户端。
- 集中托管的多租户云服务。
- 不同助手实例之间的会话、记忆或文件合并。
- 完整 VPS 文件系统双向镜像。
- Google Tasks 等外部任务工具同步。
- 多引擎切换、Bot 团队或复杂应用管理界面。

## 8. 开发任务与交付安排

服务端与安卓端使用同一份 PRD，在同一仓库配套开发。代码开发可在 VPS 上进行，Linux 服务端可在该环境部署和验证；安卓安装包构建、手机体验验证与 Windows 服务端运行验证分别完成，不将 VPS 部署成功等同于全部产品验收通过。

开工时先区分当前实现与改造目标：仓库现有代码仍是 MDNote 安卓笔记应用，尚未实现本文档定义的绿天独立助理服务端；现有技术架构及模块文档用于理解已实现的代码，本文档与对应任务说明用于界定改造方向。发现两者存在无法解释的差异时，先核查代码并沟通，不将规划描述当作已有能力。

仓库名称已调整为 `lvtian`，应用当前仍使用原有 MDNote 名称、安卓包名及 Expo 更新配置。仓库改名不要求同步重建应用身份；展示名称调整需确认界面文案，包名、签名和更新项目的变更需另行评估，不在功能清理中顺带修改。

### 8.1 当前三个开发任务

| 顺序 | 建议任务分支 | 交付范围 | 任务说明 |
| --- | --- | --- | --- |
| 1 | `mobile-foundation` | 安卓端清理 COS 与旧个人待办，保留闪念和 WebDAV；确定基础导航方案并处理发布触发范围 | [安卓端基础改造](安卓端基础改造任务.md) |
| 2 | `server-chat` | Windows／Linux 独立服务端、安卓连接、持续主聊天、审批和重连；Linux 部署验收 | [服务端与主聊天](服务端与主聊天任务.md) |
| 3 | `server-files` | 原笔记入口接入真实服务端文件目录，默认打开用户主目录，完成浏览与约定类型的预览和下载 | [系统文件](系统文件任务.md) |

按顺序交付，每个任务使用独立工作树、分支和 PR。后一个分支在前一个任务合并后，从更新后的主分支创建，避免提前创建长期落后的分支。任务说明是开发交接草案，不代表分支已创建或代码已完成。

基础导航以五个标签的最终产品结构为目标；当前尚未定义或接通的能力不显示模拟业务结果，也不以空页面代替完成。导航调整前先形成完整界面方案并确认，必要的未就绪状态与后续启用时机在方案中说明。

### 8.2 后续任务

助理待办与新闻摘要各自形成独立功能任务，分别在编辑与进展规则、生成与阅读规则确定后创建分支。两项能力均需要安卓端与服务端配套实现，不在当前三个任务中自行补全未确定的产品规则。闪念现有行为继续保留，接入 Web Clipper 不作为当前任务。

### 8.3 部署与发布边界

- PR 的自动检查和审查通过后，按仓库规则处理合并；部署使用已明确的提交版本，记录版本、验证结果和回退方式。
- Linux 服务端使用可独立停止、重启和更新的部署方式，配置、凭据和业务数据与代码及构建产物分离。
- 先验证新部署，再替换日常使用的服务；不能将开发工作树或其他任务的未提交内容直接作为正式部署来源。
- 安卓端通过独立的 APK 或兼容的热更新交付；仅部署 VPS 服务端不会更新手机 App。
- 现有工作流可能在合并 PR 时发布安卓正式热更新。第一个任务需收缩触发范围，避免纯服务端或文档改动触发安卓发布；不以调整工作流替代完整发版验证。
- Windows 平台继续属于首版范围。在 VPS 上只能完成部分跨平台检查，未完成的 Windows 运行验收必须明确列出。

## 9. 验收原则

- 所有功能均以真实服务端与安卓 App 的完整操作链路验收，静态检查和模拟接口不能代替联调结果。
- Windows 与 Linux 分别验证安装、启动、停止、重启和数据保留。
- 主聊天覆盖正常执行、等待人工处理、断网、重新连接和服务重启后的实际状态。
- 手机退出后已受理任务的实际行为与呈现一致；不承诺机器或进程中断后的自动续跑，恢复策略另行验证。
- 待办能够表达需要人处理、助理处理及双方协作的事项。
- 主聊天、助理待办、新闻摘要和系统文件使用同一助手实例的数据；闪念保留独立的 WebDAV 数据来源，不与助理数据混用。
- 清理 COS 和旧待办后，现有闪念的记录、阅读、编辑与同步仍可正常使用，云端原文不因功能退出而被删除。
- 操作失败、数据尚未提交和任务尚未完成，都有准确的状态反馈。

## 10. 下一步需确定的产品事项

1. 主聊天的持续对话与另开话题规则。
2. 闪念在保留现有能力基础上的后续扩展及助理介入方式。
3. 待办的编辑、进展确认、日期与自动执行边界。
4. 新闻摘要的主题、来源、生成时机和通知方式。
5. 系统文件的可访问范围、预览类型及管理操作。
6. 首次连接、认证、模型配置和必要设置的产品流程。

以上事项确定后，再完成相应技术设计与界面方案，不将建议方案自动视为最终实现要求。
